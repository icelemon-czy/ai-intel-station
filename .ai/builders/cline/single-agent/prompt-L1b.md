# Cline 构建 L1 代码导航文档 — Phase 4-5（单 Agent + 人工审核）

> **前置条件**：已完成 `prompt-L1a.md`（与 `builders/cline/prompt-L1a.md` 共用），且 `.ai/L1-codebase-map/_handoff.md` 已存在。
> **本文件产出**：features/[name]/ 完整文档 + infrastructure/ 完整文档 + architecture.md + module-map.md + key-files.md
>
> **与标准版的区别**：
> - ❌ 不使用 subagents — 主 agent 自己分析所有功能和基础设施
> - ⏸️ 每分析完一个功能/组件，暂停等人类审核
> - ✅ 适用于：对产出质量要求高、需要逐项把关的场景

---

## Prompt

```markdown
# 任务：构建项目代码导航文档（L1）— Phase 4-5（单 Agent 逐项分析）

## 工作模式

> **重要**：本任务不使用 subagent。你（主 agent）亲自分析每个基础设施组件和每个功能。
> 每完成一个组件/功能的文档后，**必须暂停**，输出文档内容，等待用户确认「继续」后再进入下一个。
> 禁止一次性分析多个功能。

## 准备工作

首先执行：
```bash
cat .ai/L1-codebase-map/_handoff.md
```

读取后，你将获得：基础设施层、功能清单、跨功能通用模式、补充上下文（如有）、overview.md 全文。这是本对话的全部背景。

读取后，列出完整的分析队列：

```
分析队列：
  基础设施：[组件1], [组件2], ...（如有）
  功能：[功能1], [功能2], [功能3], ...
当前进度：0 / N
```

然后从队列第一项开始。

---

> **构建顺序**：先建基础设施（地基），再分析功能（建在基础设施之上）。

### Phase 4a: 逐个分析基础设施组件（如有）

> 如果 `_handoff.md` 中「基础设施层」为「无」，跳过本步，直接进入 Phase 4b。

首先读取模板：
```bash
cat .ai/L1-codebase-map/infrastructure/_infrastructure-template/README.md
```

然后**逐个**处理每个基础设施组件，每个组件按以下 3 步执行：

#### Step 1 — 组件发现（先看代码，再输出清单）

对当前组件，执行 `cat [代表文件]` 实际阅读代码。

阅读完后，输出组件信息：

| 组件名（项目词汇） | 代表文件 | 职责一句话 |
|------------------|---------|------------|
| [填写] | [填写] | [填写] |

**命名规则**：用项目里真实存在的概念（如 framework / config / plugin-host / logger / build-system / testing），禁止用抽象通用词。

> ⚠️ 未执行 cat 命令、未阅读实际代码前，不得进入 Step 2。

#### Step 2 — 追踪依赖关系 + 发现联动

分析当前组件：
- 哪些功能层使用了它？（grep import / require / from 的引用）
- 组件之间的依赖关系是什么？（如：插件系统依赖配置系统）
- 改了组件 A，哪些看似无关的东西也要改？
- 有 TODO/FIXME/HACK 的坑？

#### Step 3 — 创建文档文件

参照模板格式，在 `.ai/L1-codebase-map/infrastructure/[组件名]/` 下创建文件：
- `README.md` — 组件概览 + 分层导航 + 关键文件 + 核心机制 + 对外接口
- `[层名].md` — 如果组件内部有多层结构，按层拆分（简单组件只需 README.md 即可）

#### ⏸️ 暂停点

创建完当前组件的文件后，输出：

```
✅ 基础设施组件「[组件名]」文档已创建。
   文件：[列出创建的文件]

分析队列进度：X / N
   ⬜ [下一个待分析项]
   ...

👉 请检查以上文档，确认无误后输入「继续」。
```

**等待用户确认后，再处理下一个组件。**

---

所有基础设施组件完成后，更新 `infrastructure/README.md`：填入组件索引表、架构全景、变更影响、已知陷阱。然后进入 Phase 4b。

---

### Phase 4b: 逐个分析每个功能（核心步骤）

> 主 agent 按 `_handoff.md` 功能清单的顺序，**一次只分析一个功能**。
> 每个功能完成后暂停等待人类审核。

对每个功能，按以下步骤执行：

#### Step 1 — 层次发现（先看代码，再输出清单）

> 如果 `_handoff.md` 中有「补充上下文」，将其作为参考背景来识别层次和命名。

1. 执行 `cat [入口文件路径]` 阅读入口文件
2. 顺着调用链，对每一层的代表文件执行 `cat [文件路径]` 实际阅读
3. **阅读完代码后**，输出层次清单：

| 层名（项目词汇） | 代表文件 | 职责一句话 |
|----------------|---------|------------|
| [填写] | [填写] | [填写] |

**命名规则**：用项目里真实存在的概念（如 handler / service / repo / proto / worker），**禁止直接使用 entry / logic / data 通用词**。

> ⚠️ 未执行 cat 命令、未阅读实际代码前，不得进入 Step 2。

#### Step 2 — 追踪数据流 + 发现联动

以 `_handoff.md` 中的「追踪起点函数/方法」为起点，追踪该功能最核心的 1-2 个操作的完整路径。
同时找出：
- 改了文件 A，哪些看似无关的文件 B 也要改？
- 有 TODO/FIXME/HACK 的坑？

#### Step 3 — 创建功能文档

读取模板参考：
```bash
cat .ai/L1-codebase-map/features/_feature-template/README.md
```

在 `.ai/L1-codebase-map/features/[功能名]/` 下创建文件：
- `README.md` — **必须包含「分层导航」表**（每行对应一个层文件，写明加载时机和内容摘要），然后是数据流、变更影响表、已知陷阱
- `[层名].md` — 每层一个文件，详细记录该层的职责、关键文件、API、陷阱

README.md 中的「分层导航」表格式：
```markdown
## 分层导航
| 层文件 | 加载时机 | 包含内容摘要 |
|--------|---------|-------------|
| handler.md | 改 API 入口 / 加新端点时 | 路由注册、请求处理 |
| service.md | 改业务逻辑 / 加新规则时 | 核心规则、状态机 |
```

#### ⏸️ 暂停点

创建完当前功能的文件后，输出：

```
✅ 功能「[功能名]」文档已创建。
   文件：[列出创建的文件]

分析队列进度：X / N
   ⬜ [下一个待分析项]
   ...

👉 请检查以上文档，确认无误后输入「继续」。
```

**等待用户确认后，再处理下一个功能。**

### Phase 5: 填写 architecture.md + module-map.md + key-files.md

> 所有功能和基础设施分析完成后执行本步。

使用 `_handoff.md` 中“跨功能通用模式”部分，结合各 feature 和 infrastructure 文档：

- **architecture.md** — 运行时架构：部署拓扑、请求生命周期、Feature ↔ Infrastructure 运行时协作表、启动顺序、中间件管道、错误传播路径、关键运行时配置
- **module-map.md** — 依赖拓扑（ASCII 全局依赖图）、模块公开 API、依赖规则、跨功能的变更联动
- **key-files.md** — 通用任务食谱（不属于单一功能的）、调查起点

> 💡 **依赖拓扑**：在 module-map.md 中生成一张 ASCII 依赖图，展示功能层 → 基础设施层的全局依赖关系。参考模板中的「依赖拓扑」部分。

## 约束
- 每个 feature 文件自包含，可独立加载
- 不确定的地方写 `[待确认：xxx]`
- **检验标准**：每一行都问"AI 从代码中能推导出来吗？"如果能，删掉
```

## 补充说明

### 质量检验清单

| 检查项 | 通过标准 | 不通过的例子 |
|--------|----------|-------------|
| feature 文件是否自包含？ | 只读这一个文件就够做该功能的任务 | ❌ 还要去 overview 查数据流 |
| README 是否有分层导航表？ | 每行对应一个层文件，写明加载时机 | ❌ README 没有导航表，AI 不知道该加载哪个分层文件 |
| 是否可推导？ | AI 不能从 tree + grep 快速推导出来 | ❌ "auth 模块在 src/auth/ 目录下" |
| 是否面向任务？ | 有具体的文件路径和步骤 | ❌ "改了 model 要更新相关文件" |
| feature 文件名是否反映实际架构？ | 文件名来自项目真实概念 | ❌ 所有功能都是 entry.md / logic.md / data.md |

### Agent 职责划分（本文件范围）

```
主 Agent（Cline）—— 本对话，单 agent 模式
├── 读取 _handoff.md（基础设施层 + 功能清单 + 跨功能模式 + overview 全文）
├── 列出分析队列
├── Phase 4a：逐个分析基础设施组件（每个完成后 ⏸️ 暂停）
├── Phase 4b：逐个分析每个功能（每个完成后 ⏸️ 暂停）
│     ├── 【功能: user-auth】  → 分析 → 创建文件 → ⏸️ 等待确认
│     ├── 【功能: order-mgmt】 → 分析 → 创建文件 → ⏸️ 等待确认
│     └── 【功能: ...】
└── Phase 5：所有分析完成后，填写 module-map.md + key-files.md
```
